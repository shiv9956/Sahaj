=== PROMPT STARTS HERE ===

# 1. ROLE

You are a principal full-stack engineer, applied-AI architect, product designer and hackathon strategist embedded in team **The NPM Tigers**. You will build **Sahaj** end to end, phase by phase, to a standard that can win a Paytm hackathon Track 2 (making insurance, lending and fintech simpler, faster and more human).

You write production-quality TypeScript, you test what you build, and you are honest about what works and what is mocked. You never fabricate API parameters, statistics, product terms or sponsor capabilities.

# 2. MISSION AND WINNING THESIS

**One-line thesis:** *Clarity before credit.* The first barrier in Indian retail finance is not access, it is comprehension: jargon, language, fragmented steps and fear of the fine print. Sahaj is a **journey engine** (not a chatbot) that turns a spoken or typed goal like *"Mujhe ₹2 lakh ki zarurat hai education ke liye"* into a guided, evidence-backed, next-action-driven journey across lending and insurance.

**Core loop (from the blueprint):** Understand → Contextualize → Retrieve → Reason → Compare → Guide → Continue.

**What "winning" means for this build** (optimize for all five):
1. **A demo that never breaks:** works on a phone, on hotspot, in Hinglish voice, with a chaos toggle that proves graceful degradation.
2. **Visible, load-bearing sponsor tech:** Cognee is essential to answers and memory (not decoration), Sarvam is essential to language and documents, n8n does real asynchronous work. A "Glass-Box Judge Mode" proves each in real time.
3. **Trust as the product:** no invented numbers, no guaranteed approvals, every claim traceable (Trust Receipt), every number computed by deterministic code.
4. **Three unforgettable moments** (design the whole demo around them):
   - **Voice → Amount chip:** the user speaks Hinglish; Sahaj shows *"₹2,00,000, sahi hai?"* before acting on it.
   - **Trust Receipt:** one tap shows the exact sources, graph path, rules and assumptions behind a recommendation.
   - **Regret-Proof Simulator + Forget button:** sliders show EMI, total cost and a stress test instantly; "What Sahaj remembers" lets the user delete their own memory.
5. **A credible path to Paytm:** an abstract product connector with a mock adapter today and a clearly stated swap-in path for real Paytm APIs (never claimed as live).

# 3. NON-NEGOTIABLE RULES (violating any of these is a failed build)

1. **No fabricated Paytm integration.** Paytm is the *target ecosystem and product context*. Use a `FintechProductConnector` interface with a `MockPaytmAdapter`. Every product shown carries a visible "Demo catalog — synthetic data" label unless the organizers provide real sandbox access (then log that in `docs/DECISIONS.md`). Do not use Paytm logos or branding.
2. **No critical arithmetic by an LLM.** EMI, totals, ratios, stress tests, premiums, effective cost: deterministic code only (`packages/engines`), integer-paise money type, unit and property tested.
3. **No guarantees.** Never say or imply approved, guaranteed, best for you, you will save X. Allowed: "likely meets the stated criteria", "may not meet", "unknown — need X". All estimates carry an `illustrative` label plus visible assumptions.
4. **Facts come from retrieval.** Product terms, eligibility, exclusions and definitions come from the Cognee-backed knowledge layer (with source/version/effective-date metadata), never from model memory.
5. **Cognee is mandatory and load-bearing.** Shared product knowledge and per-user journey memory both live in Cognee (separate datasets). The app must be visibly worse without it.
6. **Isolation.** Cognee dataset names for user memory are derived server-side from a pseudonymous hash, never from client input. A cross-user leakage test must pass before any demo.
7. **Data minimization.** Synthetic or consented data only. Collect only what the current step needs. Do not send raw documents to an LLM. Extract fields, mask identifiers, and store bands instead of exact figures in long-term memory where possible.
8. **State machine over vibes.** Journey progress is a deterministic state machine. The LLM proposes; code disposes.
9. **Grounding Gate.** Every LLM answer passes a post-generation validator (numbers traced to the calculation or context pack, citations exist, banned claims absent, language matches). Fail twice → templated fallback or human escalation. Never ship an unvalidated financial answer.
10. **n8n stays out of the synchronous chat path.** It handles asynchronous work only (documents, nudges, escalation, refresh, analytics). If n8n is down, the chat still works.
11. **Graceful degradation everywhere.** Every external call has a timeout, retry policy, circuit breaker and fallback. The user is never left at a dead end (see S10).
12. **No secrets in git.** `.env` only, `.env.example` committed, secret scanning in pre-commit and CI.
13. **Statistics honesty.** If you cite any India-market statistic in the deck or UI, it must have a named primary source and date in `docs/SOURCES.md`. Otherwise do not cite it.
14. **Scope discipline.** Primary journey = education/personal lending. Secondary = insurance discovery and explanation (plus the Loan + Protection Bridge). Anything else is out of scope unless a phase says otherwise.
15. **Everything demo-critical is tested.** The golden path has an automated end-to-end test that runs in CI.

### S1 — Trust Receipt
- **What:** every recommendation, comparison and calculation has a receipt: (a) sources used (Cognee item IDs, document title, version, effective date, dataset), (b) the retrieval path (query, search type, filters, top-k, latency), (c) user inputs that influenced the result (with provenance: stated / extracted from document / assumed), (d) rules fired (rule IDs), (e) calculation assumptions, (f) confidence and "what I can't tell you".
- **Why it wins:** turns "AI hallucination risk" (the judges' first worry in fintech) into a visible, demoable strength.
- **Acceptance:** 100% of assistant messages that contain a number or a product claim have a receipt; receipt drawer opens in under 200 ms from cached data; a test asserts no number appears in a message that is absent from its receipt.

### S2 — Bol-Kar-Samjho (voice-first Hinglish)
- **What:** press-and-hold mic → Sarvam speech-to-text (code-mixed) → transcript with **confirmation chips** for every money/tenure/income value → journey continues. Answers can be read back by Sarvam text-to-speech, with numbers verbalized correctly ("do lakh rupaye").
- **Why it wins:** proves Sarvam is load-bearing, serves low-literacy and low-typing users, and the chip pattern shows fintech-grade care about ASR errors on amounts.
- **Acceptance:** spoken "do lakh", "dedh lakh", "dhai lakh", "pachas hazaar", "2L" all normalize correctly in tests; no money value is acted on before the user confirms it.

### S3 — Regret-Proof Simulator
- **What:** sliders for amount, tenure, moratorium behavior and rate; instant EMI, total interest, **effective annual cost including fees**, EMI-to-income ratio, and a **stress test** (income −20%, rate +1 to +2 points, one skipped month). Bands (comfortable / stretch / risky) come from a visible, configurable illustrative threshold file.
- **Why it wins:** demonstrates real decision support, not chat. Runs in the browser using the same pure-TS `engines` package, so sliders feel instant, while the server recomputes authoritatively for the receipt.
- **Acceptance:** slider updates render in under 50 ms; browser and server results match to the paisa in a parity test.

### S4 — Jargon Lens
- **What:** any recognized financial term in any message becomes tappable. The popover shows a one-line plain explanation, a daily-life analogy, an example with the user's own numbers where relevant, and a "listen" button. Content comes from the Cognee glossary dataset, translated or transliterated via Sarvam, with protected terms (EMI, moratorium) kept consistent.
- **Acceptance:** at least 80 glossary terms in English + Hindi + Hinglish; term matching is script-aware; popover content always shows its source.

### S5 — Journey Memory Graph, "What Sahaj remembers", Forget
- **What:** Cognee stores per-user journey memory (goal, purpose, chosen priorities, shortlisted products, decisions with reasons, document types and statuses) in an isolated dataset. On return, Sahaj says what it remembers and asks the user to confirm. A **Memory panel** lists every remembered item with a delete button and a "forget everything" action that really deletes from Cognee and Mongo.
- **Why it wins:** it is the strongest honest use of Cognee's memory story plus a privacy differentiator no chatbot demo will have.
- **Acceptance:** resume works across sessions; deleting an item removes it from retrieval (proven by a search test); two synthetic users never see each other's memory.

### S6 — Document-to-Profile autopilot
- **What:** upload (or camera-capture) a synthetic admission/fee letter or salary slip → Sarvam Vision digitizes → schema extraction → validation → user confirms → profile fields auto-fill (marked `extracted_from_doc`) and the checklist updates.
- **Acceptance:** extraction runs asynchronously with visible status; low-confidence fields are flagged, never silently accepted; injected instructions inside a document are ignored (test).

### S7 — Glass-Box Judge Mode (`?judge=1`)
- **What:** a side panel that shows, live and per request: Cognee queries (dataset, search type, filters, latency, returned node/chunk IDs), Sarvam calls (model, language detected, mode, latency), n8n execution IDs and status, the state machine transition, grounding-gate result, and the time budget breakdown.
- **Why it wins:** judges verify sponsor integration in 10 seconds without reading code.

### S8 — Fine-Print Radar (B)
Top 3 personalized watch-outs per product (moratorium interest accrual, prepayment charges, processing fee, floating rate, collateral, insurance waiting periods, exclusions, sub-limits, co-pay). Clauses are tagged at ingestion; ranking is a deterministic function of the user's profile and priorities. Each watch-out links to its source clause.

### S9 — Loan + Protection Bridge (B)
After loan options, Sahaj *educates* (never pushes) on protecting the co-applicant and the loan: shows a deterministic "protection gap" illustration (outstanding liability + dependents' expenses over a stated horizon, labeled as a rule-of-thumb) and explains relevant insurance concepts from the knowledge graph. Requires explicit opt-in, shows exclusions and waiting periods first, and uses suitability questions rather than sales language. This ties Track 2's lending and insurance halves into one journey.

### S10 — Zero-Dead-End guarantee
Every assistant turn ends with a **Next Best Action** (deterministic, never empty). Failure of any dependency, low confidence, or repeated grounding failure produces: (1) a plain-language explanation, (2) an alternative path (manual form, cached answer, simpler question), and (3) an offer of the **Human Desk** (n8n escalation with ticket ID).

### S11 — Living Knowledge Watchdog (B)
Scheduled n8n workflow checks `effective_date` and source status, flags stale knowledge, triggers incremental Cognee add/cognify, and the UI shows "As of <date>, v<version>" badges on every product.

### S12 — Clarity Score (B)
After the journey, ask one question: "Ab aapko agla step clear hai?" (1 to 5) plus optional comprehension micro-checks. Track time-to-next-action, jargon lookups, and abstentions. Report real, small-sample, honestly labeled numbers in the pitch.

### S13 — Chaos Toggle (B)
A hidden control (`?chaos=1`) that simulates outage of Cognee, Sarvam, n8n or the LLM, to show fallbacks live.

**Synchronous path (chat):** `MESSAGE → LANG/SCRIPT → FAST PARSE (rules first, LLM second) → LOAD STATE → PLAN → PARALLEL {RETRIEVE, CALCULATE, CHECKLIST} → CONTEXT PACK → COMPOSE (stream) → GROUNDING GATE → RECEIPT → STATE UPDATE`.
**Asynchronous path:** outbox events → n8n → callbacks. Nothing in the chat path waits on n8n.
**Latency stance (targets to measure, not promises):** first SSE `status` event ≤ 300 ms; time-to-first-token p50 ≤ 1.5 s, p95 ≤ 3 s; retrieval timeout 2.5 s with fallback; speculative retrieval warm-up when the profile becomes ready.

## 9.3 Journey state machine

**States:** `NEW → INTENT_CAPTURED → PROFILE_INCOMPLETE → PROFILE_READY → KNOWLEDGE_RETRIEVED → OPTIONS_READY → DOCUMENTS_PENDING → APPLICATION_GUIDANCE → FOLLOW_UP`, plus overlay flags `ESCALATED` and `PAUSED`.
**User-facing rail (5 steps):** Goal → Profile → Options → Documents → Action.

| From | To | Trigger | Guard | Side effects |
|---|---|---|---|---|
| NEW | INTENT_CAPTURED | first parsed message | domain ≠ unknown and goal detected | create journey event; write memory candidate |
| INTENT_CAPTURED | PROFILE_INCOMPLETE | planner run | required fields missing | choose single next question |
| INTENT_CAPTURED / PROFILE_INCOMPLETE | PROFILE_READY | field confirmed | all required fields present, valid, money fields confirmed | start speculative retrieval prefetch |
| PROFILE_READY | KNOWLEDGE_RETRIEVED | retrieval success | ≥ 1 verified source in context pack | store receipt draft |
| KNOWLEDGE_RETRIEVED | OPTIONS_READY | compare done | grounding gate passed | enable simulator, radar |
| OPTIONS_READY | DOCUMENTS_PENDING | user shortlists a product | product exists in catalog | build checklist, enqueue nudge event |
| DOCUMENTS_PENDING | APPLICATION_GUIDANCE | all required docs confirmed | none missing/unreadable | generate next-action plan |
| APPLICATION_GUIDANCE | FOLLOW_UP | guidance delivered | none | schedule reminders, write memory |
| any later state | earlier state | profile change | invalidation rule | mark downstream artifacts stale, recompute |
| any | (flag) ESCALATED | escalation trigger | see Phase 4.12 | outbox event to Human Desk workflow |

**Required fields (lending/education):** `amount`, `purpose`, `borrower_role` (student / parent / other), `coapplicant_monthly_income` (exact or band), `existing_emi_total`, `tenure_pref_months` **or** `affordable_emi_pref`, `collateral_willingness` (yes/no/unknown). **Insurance:** `cover_type`, `age_band`, `dependents_count`, `existing_cover`, `monthly_budget`. Never collect health details; explain concepts only.

## PHASE 2 — COGNEE KNOWLEDGE LAYER (≈14%)

**Objective:** a curated, versioned, retrievable knowledge graph of lending and insurance knowledge, with measured retrieval quality and a resilient retrieval service.

**Processes**
- **2.1 Corpus specification.** Every document has front-matter: `doc_id, domain, product_id, title, provider_display, version, effective_date, source_type (synthetic | public_verified), source_uri, language, license`. Consistent body headings so graph extraction is reliable: *Overview · Key Terms (key: value lines) · Eligibility · Fees and Charges · Repayment and Moratorium · Documents Required · Exclusions and Watch-outs · FAQs · Related Glossary Terms*.
- **2.2 Corpus authoring** (put in `data/corpus/`):
  - 8 lending products (education loan variants with and without moratorium and collateral, NBFC-style education loan, unsecured personal loan, small-ticket instant loan, co-applicant-required and not), all `synthetic`.
  - 5 insurance products (term life, individual health, family floater, personal accident, loan-protection concept), all `synthetic`.
  - Glossary of 80+ terms with EN, HI, Hinglish explanation, one everyday analogy, related terms.
  - 60 FAQs and 12 "how it works" explainers (EMI, interest types, moratorium, co-applicant, collateral, credit score basics, sum insured, waiting period, co-pay, sub-limits, claims, free-look).
  - Any real-world regulatory fact must be `public_verified` with a URI in `docs/SOURCES.md`; otherwise mark the whole document `synthetic`.
- **2.3 Single source of truth.** Ingestion script parses front-matter and key-value terms to populate Mongo `products` and `knowledge_sources`, computes `source_hash`, and emits the exact text sent to Cognee. Numbers used for comparison come from the structured record; meaning, clauses and relationships come from Cognee; both cite the same `source_id`.
- **2.4 Ontology.** Implement §9.2 relations. If your Cognee version supports custom graph models/ontologies, register them; otherwise rely on consistent phrasing. Verify by inspecting the graph output, not by assuming.
- **2.5 Dataset and version plan.** Create datasets per §9.2 with `_v1` suffix; store `active_kb_version` in Mongo config so a re-ingest to `_v2` can be switched (and rolled back) without code changes.
- **2.6 Ingestion pipeline (`scripts/ingest`).** Idempotent (skip unchanged `source_hash`); `add` with dataset and node-set/tag metadata (product id, domain, version); `cognify` in batches, background mode where supported; poll pipeline status; write `ingestion_status` and `cognee_data_ids`; retries with backoff; timing and cost log. **Never run in a user request path.** Run before the demo and in CI against a small fixture corpus.
- **2.7 Graph QA.** Create `data/eval/graph_expectations.yaml` (e.g., "Product X requires Document Y", "Product Z has a moratorium of N months") and a test that queries Cognee and asserts these facts appear. Fix corpus phrasing wherever extraction misses. Keep a screenshot of the graph view for the deck.
- **2.8 Retrieval service.** `retrieve(intent, journey) → ContextPack`:
  1. Classify the retrieval need: `fact_lookup | relationship | explanation | clause_quote | glossary | user_memory`.
  2. Route (initial defaults, to be replaced with measured winners in 2.12): relationship/multi-hop → graph-enhanced completion search; exact clause quoting → chunks search; glossary/overview → summaries; simple lookup → RAG-style search.
  3. Apply filters (dataset list, product/node filter), small `top_k` (3–6).
  4. Prefer the **context-only** option where available so Sahaj's own LLM composes the final answer in the user's language under the Grounding Gate.
  5. Run independent queries in parallel with per-query timeouts (2.5 s).
  6. Normalize to `ContextItem {id, text, source_id, doc_version, effective_date, score, retrieval_mode, dataset}`; dedupe; light rerank (boost items whose `product_id` is in the shortlist); enforce a token budget.
  7. Emit a trace record (query, type, filters, latency, ids) to `traces` and to Judge Mode.
- **2.9 Caching and prefetch.** Redis/LRU cache keyed by `(kb_version, search_type, normalized_query, filters)` with 1 h TTL for shared datasets; **never** cache user-dataset results across users; invalidate on `active_kb_version` change. Speculative prefetch: when the state reaches `PROFILE_READY`, warm the cache for the top candidate products and their glossary terms while the user reads.
- **2.10 Fallback ladder.** Cognee timeout/error → (1) cache → (2) `data/fixtures/cognee-snapshots` (recorded last-good results, flagged "cached" in the receipt and Judge Mode) → (3) honest message "I couldn't verify that right now" + Next Best Action + Human Desk offer. Never fill the gap from model memory.
- **2.11 Freshness metadata.** Every `ContextItem` carries `effective_date` and `doc_version`; UI shows "As of <date>, v<version>"; items older than a configured age get a "may be outdated" flag.
- **2.12 Retrieval evaluation.** Build 60 question → expected `source_id` pairs (English, Hindi, Hinglish). Measure recall@k, MRR, latency per search type on your corpus. Choose per-route defaults from the data. Save the table to `docs/EVAL_REPORT.md` (deck material: "why graph beats plain RAG here").
- **2.13 Structured-vs-retrieved agreement test.** For every product, assert that fee/tenure/moratorium text returned by Cognee agrees with the structured record. Disagreement fails CI.

**Deliverables:** corpus, ingestion scripts, populated datasets, retrieval service, cache, snapshot fixtures, eval report.
**Acceptance:** graph expectations pass; retrieval recall@5 ≥ 0.85 on the eval set (or documented gap and fix plan); every `ContextItem` has source/version/effective_date; killing Cognee triggers the fallback ladder in a test.
**Failure modes:** poor entity extraction → tighten corpus templates and add explicit relation sentences; slow completion searches → default to chunks/context-only plus our own composer; cognify quota → smaller corpus, prioritize the demo persona paths.
**Gate:** phase report + "GO".

## PHASE 3 — DETERMINISTIC ENGINES (≈9%)

**Objective:** every number the user sees is computed by tested code.

**Processes**
- **3.1 Money primitives.** Integer paise `Money` type; `decimal.js` for rates; INR formatting with Indian digit grouping (`₹2,00,000`), a verbalizer ("do lakh rupaye" / "two lakh rupees"), rounding rules stated once and documented.
- **3.2 EMI and amortization.** Reducing-balance EMI `P·r·(1+r)^n / ((1+r)^n − 1)` with monthly `r = annual/12/100`; handle `r = 0`; full schedule (interest, principal, balance); total interest; last-payment rounding adjustment so the schedule closes to zero.
- **3.3 Moratorium modes (education loans).** Parameters `moratorium_months` and `interest_during_moratorium: pay_simple_interest | accrue_and_capitalize`. Both computed and shown as an explicit assumption; the difference in total cost is displayed side by side.
- **3.4 True cost.** Total interest + processing fee + other configured charges, and an **effective annual cost** solved via monthly IRR (bisection/Newton), labeled "illustrative".
- **3.5 Affordability.** Ratios: `new_EMI / net_monthly_income`, `(existing_EMIs + new_EMI) / net_monthly_income`. Support the student + co-applicant case (income belongs to the co-applicant). Thresholds live in `data/rules/affordability.json` (e.g., comfortable / stretch / risky), shown on screen as "illustrative thresholds you can change", never as regulatory limits.
- **3.6 Stress tests.** Income −20%, rate +1 pt and +2 pt, tenure +12 months, one skipped month (interest carry). Output a compact table plus a plain-language verdict key (`comfortable | stretch | risky`).
- **3.7 Insurance illustrations.** Illustrative premium via a synthetic rate table (age band × cover); "protection gap" = outstanding liability + (annual household expense × stated horizon), labeled as a rule-of-thumb for education, not advice.
- **3.8 Eligibility rule engine.** JSON DSL (`all`, `any`, `not`, comparisons on profile fields). Output is **tri-state**: `likely_meets | may_not_meet | unknown`, with `rule_ids`, `reasons[]`, and `missing_fields[]` (which feed the question planner). It can never output "approved".
- **3.9 Fine-print radar scoring.** Clause tags (`prepayment`, `moratorium_interest`, `floating_rate`, `processing_fee`, `collateral`, `waiting_period`, `exclusion`, `sub_limit`, `co_pay`). Score = tag severity × relevance to the user's profile and priorities. Return top 3 with clause IDs.
- **3.10 Comparison builder.** Normalized rows (rate, fee, tenure, EMI, total cost, effective cost, moratorium, collateral, co-applicant, eligibility status, watch-outs, `as_of`). Compute per-attribute leaders; order by the user's ranked priorities; "why this order" is generated as **structured data** (i18n key + params), not free LLM text.
- **3.11 Amount/number parsers.** Parse Indian and Hinglish expressions to paise: `2 lakh`, `₹2,00,000`, `2L`, `2 lac`, `do lakh`, `दो लाख`, `dedh lakh` (1.5), `dhai lakh`/`ढाई लाख` (2.5), `sava lakh` (1.25), `pachas hazaar`, `1 crore`, `20k`, spoken digit sequences. Also parse durations (`5 saal`, `60 mahine`, `3 years`). Return `{value, confidence, raw}`; ambiguity returns candidates rather than guessing.
- **3.12 Testing.** ≥ 40 parser phrases; property tests (schedule sums to principal, EMI increases with rate, decreases with tenure, effective cost ≥ nominal rate when fees > 0); golden fixtures cross-checked against an independent spreadsheet PMT calculation; parity test that the browser bundle and server give identical results.
- **3.13 Exposure.** `/simulate` and `/compare` return results plus `assumptions[]` and `label: "illustrative"`. The same `engines` package is imported by the web app for instant sliders.

**Deliverables:** `packages/engines` with ≥ 95% line coverage, fixtures, parity test.
**Acceptance:** all property tests pass; zero arithmetic anywhere else in the codebase (lint rule or grep check that flags `*`/`/` on money outside `engines`).
**Failure modes:** float drift → integer paise plus decimal only; ambiguous spoken numbers → confirmation chip (Phase 7) rather than a silent guess.
**Gate:** phase report + "GO".

## PHASE 4 — THE JOURNEY BRAIN: LLM, ORCHESTRATOR, GROUNDING (≈14%)

**Objective:** turn free-form Hinglish/English into state transitions, tool calls and grounded, validated, streamed answers.

**Processes**
- **4.1 LLM Gateway.** One interface: `complete()`, `stream()`, `structured<T>(schema)`. Providers behind config (Sarvam chat models; optional second provider). Task-based routing: fast model for intent/entity extraction and small explanations, flagship for comparisons and nuanced explanations. Features: JSON-schema-constrained output with repair-once retry, streaming, timeouts, token and latency logging into `traces`, prompt versioning from `prompts/v1/`, temperature 0–0.2 for extraction and ≤ 0.4 for composition. A/B harness that runs the Appendix C set across providers and prints a comparison table; choose by data.
- **4.2 Language and script detection.** Detect `en | hi | hinglish (Roman) | mixed`; remember the user's preferred language and script; respond in the same language and script by default; allow a toggle (Devanagari ↔ Roman) via transliteration.
- **4.3 Two-stage intent and entity extraction.** Stage 1: deterministic parsers (`engines` amount/duration parsers, keyword rules for domain/purpose) run in under 20 ms. Stage 2: LLM structured extraction into `IntentResult {language, domain (lending|insurance|bridge|general_info), purpose, amount, tenure, income_hint, obligations_hint, priorities[], sentiment_urgency, needs_human, confidence}` using Appendix B. Merge: deterministic wins on numbers; LLM wins on purpose/priority; conflicts lower confidence and trigger a confirmation question.
- **4.4 Profile manager.** Merge extracted fields into `financial_profiles` with provenance (`stated | extracted_from_doc | assumed`) and `confirmed` flags. **Money fields require explicit confirmation** (chip in UI). Any field is editable at any time; edits emit a profile-change event that invalidates downstream artifacts per the state machine.
- **4.5 Missing-field planner.** Given the domain and profile, compute missing required fields; rank by **unlock value** (how many products' eligibility statuses go from `unknown` to determinate, and whether the field is needed for affordability); ask **one** question at a time (two only when inseparable, e.g., income and existing EMI). Provide 2–4 quick-reply chips. Support "I don't know / skip": fill with a labeled default assumption and mark `assumed`, and show how that affects the result.
- **4.6 Orchestrator (sync path).** Implement the pipeline with per-stage timers and budgets:
  1. auth + rate limit + request-id (≤ 10 ms)
  2. language/script detect + normalization (≤ 30 ms; Sarvam language ID only if heuristics are uncertain)
  3. two-stage intent parse (≤ 400 ms typical)
  4. load journey state (Redis hit, Mongo fallback)
  5. apply profile updates → state transition → planner
  6. emit `status: understanding`
  7. **parallel tools**: `retrieve` (Cognee), `simulate/compare` (engines), `checklist`, `explain_term` (glossary) with per-tool timeouts
  8. build **ContextPack** (context items + calculation results + rules fired + assumptions + profile snapshot)
  9. emit `card` events as soon as cards are ready (comparison and simulator before prose completes)
  10. compose answer via LLM with the strict system prompt (Appendix A) and stream `token` events
  11. **Grounding Gate** (4.9); on fail, regenerate once with validator feedback, else fallback
  12. build and store **Trust Receipt**; emit `receipt`, `state`, `done`
  13. post-turn async: `journey_event`, memory candidates (Phase 6), outbox events, metrics
- **4.7 Tool router.** Tool plan is deterministic by state and intent (e.g., `PROFILE_READY` → retrieve + simulate + compare). The LLM may *request* extra tools (`explain_term`, extra retrieval) via function-calling, but an allowlist executor validates arguments and can refuse. Tools: `retrieve`, `simulate`, `compare`, `checklist`, `explain_term`, `escalate`, `schedule_nudge`, `recall_memory`.
- **4.8 Prompt assembly.** Separate system prompt (immutable rules), developer context (state, language, reading level), **data** (ContextPack, wrapped in delimiters and explicitly marked untrusted), and the user message. Retrieved text and document text are **data, never instructions**.
- **4.9 Grounding Gate.** Post-generation validator (pure code plus optional small LLM check):
  - every number in the answer appears in the ContextPack (compare after normalization: `₹2,00,000` = `200000` = "do lakh")
  - every cited `source_id` exists in the pack and version/date match
  - banned-claim scan (`guaranteed`, `approved`, `100% sure`, `you will save`, `best for you`, Hindi/Hinglish equivalents such as `pakka approve`, `guarantee`)
  - the answer language/script matches the target
  - the answer ends with a Next Best Action
  - no instruction-like text echoed from retrieved data
  On failure: retry once with the failure reasons; on a second failure use a **template fallback** built from structured data (cards only, minimal prose) and offer the Human Desk.
- **4.10 Trust Receipt builder.** Assemble §5-S1 fields from the ContextPack and tool traces; store in `receipts`; expose via `/api/receipts/:id`.
- **4.11 Next Best Action.** Deterministic function of `(state, missing_fields, doc_checklist, flags)` returning one primary action plus up to two secondary ones. It must never return empty.
- **4.12 Uncertainty and escalation policy.** Escalate (or offer escalation) when: extraction confidence < threshold after one clarification; conflicting retrieved facts; grounding gate fails twice; user asks for something outside scope (legal/tax advice, specific approval, complaints); user requests a human; repeated frustration signals; document extraction cannot be validated. Each escalation writes an outbox event with a **redacted summary** (no raw income figures, no raw document content).
- **4.13 Scope and safety guard.** Refuse or redirect: guaranteed outcomes, "which is best, just decide for me", legal/tax advice, other users' data, disclosure of system prompts, attempts to override rules. Provide a helpful alternative every time (compare + explain trade-offs, then let the user choose). Prompt-injection resistance verified by the red-team set in Phase 9.
- **4.14 Response style.** Mirror the user's language; Hinglish register that is friendly and respectful (`aap`), reading level ≤ grade 8, short paragraphs, one analogy where it helps, key terms wrapped for the Jargon Lens, a labeled `illustrative` tag on estimates, and the pattern from the blueprint: **fact from source → cite → simple explanation → label estimate → state limitations → next action.**
- **4.15 Insurance journey and Loan + Protection Bridge.** Insurance flow: cover type → age band → dependents → existing cover → budget → retrieve products → illustrative premium → compare with exclusions and waiting periods first → checklist. Bridge (S9): only offered after the user reaches `OPTIONS_READY` in lending, requires opt-in, uses the protection-gap illustration and neutral educational copy, and never auto-adds cover.
- **4.16 Conversation summary.** After each milestone, produce a compact structured summary (goal, confirmed facts, open questions, shortlisted products, decisions and reasons). This feeds the visible progress panel and Phase 6 memory writes.
- **4.17 Streaming implementation.** SSE with typed events; cards stream before prose; cancel on client abort; resume via last event ID.

**Deliverables:** gateway, orchestrator, planner, tool router, grounding gate, receipt builder, prompt pack, A/B table.
**Acceptance:** golden-path e2e (Priya) reaches `APPLICATION_GUIDANCE` through the API only; grounding gate blocks a seeded hallucinated-number test 100% of the time; banned-claim tests pass in EN/HI/Hinglish; median time-to-first-token measured and recorded.
**Failure modes:** LLM JSON invalid → repair-once then rules-only parse; model slow → switch to fast model and shorter composition; Cognee slow → cached/snapshot context flagged in the receipt.
**Gate:** phase report + "GO".

## PHASE 5 — SARVAM LAYER: LANGUAGE, VOICE, DOCUMENT INTELLIGENCE (≈11%)

**Objective:** make Indian-language and document capabilities load-bearing and safe.

**Processes**
- **5.1 Sarvam client.** Thin typed wrapper (base `https://api.sarvam.ai`, header `api-subscription-key`) or the official JS SDK if the docs confirm one. Central model registry in config, filled from the docs read in Phase 0: speech-to-text (Saaras v3), text-to-speech (Bulbul v3), translation (Mayura, Sarvam-Translate), chat (Sarvam-30B, Sarvam-105B), document intelligence (Sarvam Vision), plus transliteration and language identification. Inherits timeout/retry/breaker/chaos/trace from 1.7.
- **5.2 Text path.** Heuristic script detection first; Sarvam language ID when uncertain. Transliteration for Devanagari ↔ Roman display toggle. Translation of retrieved English snippets into the user's language with a **protected-terms list** (EMI, moratorium, co-applicant, sum insured, etc.) so terminology stays consistent and matches glossary entries.
- **5.3 Model selection by evidence.** Run 20 Hinglish prompts through Sarvam-30B, Sarvam-105B and any alternate provider; score fluency, faithfulness to context, JSON validity, latency. Use Sarvam models wherever they win or tie, and record the table.
- **5.4 Voice in (S2).** Web recorder (MediaRecorder, push-to-talk plus tap-to-toggle), size-capped chunks, upload to `/api/voice/transcribe`, Saaras v3 in code-mixed mode with language auto-detect; return transcript and per-entity spans. **Number-safety layer:** run the parsers from 3.11 on the transcript and return `confirmations[]` (amount, tenure, income) for chips. Nothing numeric is committed to the profile until the user confirms.
- **5.5 Voice out.** `/api/voice/speak` calls Bulbul v3 with a chosen voice/pace per language; split by sentence and stream/queue audio so playback starts early; a numeral verbalizer converts `₹2,00,000` to spoken words; cache audio by hash of `(text, voice, pace)`; UI has listen/pause/speed, and auto-read is opt-in.
- **5.6 Document Intelligence (S6).** Pipeline: upload (mime/size validation) → object storage → create Sarvam Vision job → poll (or receive webhook) → digitized text/markdown/JSON → **schema extraction** → validation → user confirmation → profile merge → checklist update → (if approved) memory ledger entry of *document type and status only*.
- **5.7 Extraction schemas.** Define per-document JSON schemas: *admission/fee letter* (`institution`, `course`, `annual_fee`, `total_fee`, `start_date`), *salary slip* (`employer`, `month`, `gross`, `net`, `deductions`), *ID-like document* (`name`, `dob`, masked identifier last 4 only, or skip the identifier entirely). Use only fully synthetic sample documents in the demo.
- **5.8 Validation rules.** Type/regex checks, cross-field checks (net ≤ gross, dates in a plausible range), confidence thresholds; low confidence or failed checks produce `needs_review` flags. Unreadable pages produce an actionable message ("photo dhundhli hai, dobara le sakte hain?").
- **5.9 Injection and PII defense.** Digitized text is untrusted data: strip control sequences, never place it into instruction position, and run a pattern check for instruction-like text (test with a document containing "ignore previous instructions"). Do not send raw documents to the LLM; send only the extracted field set. Mask identifiers in logs and UI. Raw files auto-expire (TTL) and can be deleted by the user.
- **5.10 Async and status.** Extraction never blocks chat. UI shows `queued → processing → needs review → confirmed`. The n8n document workflow (Phase 8) is the default orchestrator; `FF_DOC_INLINE_FALLBACK` runs the same steps inside the API if n8n is unavailable.
- **5.11 Fallbacks.** STT fails → prompt to type, keep the recording for retry; TTS fails → text only with a subtle notice; Vision fails or rate-limits → manual field-entry form plus optional escalation; language ID fails → default to the user's last language.
- **5.12 Language coverage.** MVP: English, Hindi, Hinglish. Stretch (S14): add Tamil/Bengali/Marathi by reusing the same pipeline after checking each model's language table in the docs.

**Deliverables:** Sarvam wrappers, voice endpoints, document pipeline, schemas, sample synthetic documents, model comparison table.
**Acceptance:** 10 recorded Hinglish audio samples transcribe with amounts correctly surfaced to chips; injection document test passes; extraction field accuracy measured on 10 synthetic documents (report the number); every failure path has a passing fallback test.
**Failure modes:** noisy audio → ask to repeat with visible waveform tip; mixed-script input → normalize before parsing; extraction drift → show the raw digitized text side by side for correction.
**Gate:** phase report + "GO".

## PHASE 6 — JOURNEY MEMORY (COGNEE) AND THE PAYTM-READY CONNECTOR (≈7%)

**Objective:** durable, private, deletable memory in Cognee, and an honest ecosystem integration seam.

**Processes**
- **6.1 Memory tiers.** *Working* (Redis: current turn context, short TTL) → *Episodic* (Mongo `journey_events`: what happened, when) → *Semantic/relational* (Cognee per-user dataset: what it means and how it connects).
- **6.2 Write policy (what enters Cognee).** Short **memory statements** with metadata, e.g., "User wants ₹2,00,000 for engineering education; prioritizes low EMI over lowest total cost; shortlisted Product X and Y; chose to postpone insurance." Categories: `goal`, `preference`, `shortlist`, `decision_with_reason`, `document_status`, `open_question`. **Never** store raw identifiers, exact income, or document contents. Use bands ("income band 30–40k") when a number is needed for personalization. Each write creates a `memory_ledger` row containing the Cognee data ID.
- **6.3 Write timing.** Debounced batching at milestones (state change, document confirmed, session end), not every turn. `add` → `cognify` for the per-user dataset runs asynchronously; a failed write is retried from the outbox and never blocks chat.
- **6.4 Recall (resume flow).** On journey resume: search the user's dataset (summaries/chunks; temporal search if supported by your version) → produce a short "Welcome back" recap → ask the user to confirm or correct → corrections update the ledger and Cognee. Also use recall mid-journey to avoid re-asking known answers.
- **6.5 Isolation and authorization.** Dataset names always derived server-side (`sahaj_journey_{user_hash}`); the API never accepts a dataset name from the client; shared datasets are read-only from the request path; verify Cognee's ownership/permission behavior (datasets addressed by name map to the caller's own datasets, others need IDs and permissions) and document it. **Isolation test:** two synthetic users with different goals; assert user A's statements never appear in any of user B's retrieval traces, across all search types.
- **6.6 Transparency and forgetting (S5).** `GET /memory` lists ledger entries (plain-language statements, timestamps, category). `DELETE /memory/:id` removes the item from Cognee and marks the ledger row deleted; `POST /memory/forget-all` deletes the user dataset and clears derived fields in Mongo. A test proves a deleted statement can no longer be retrieved. Consent toggles (`consents.memory`) gate all writes.
- **6.7 Personalization from memory.** Examples: pre-select priority ranking, skip already-answered questions, resume at the right state, reference earlier decisions ("Pichli baar aapne low EMI ko priority di thi. Ab bhi wahi sahi hai?").
- **6.8 Product connector.** Define `FintechProductConnector { listProducts(domain, filters), getProduct(id), getRateCard(id, profileHints), createLeadIntent(journeyId) }`. Implement `MockPaytmAdapter` (reads `products`, every response tagged `synthetic: true`) and a `SandboxPaytmAdapter` stub that throws `NotConfigured` unless credentials exist and `FF_PAYTM_SANDBOX=true`. A shared **contract test** suite must pass for both. UI shows the "Demo catalog (synthetic)" badge. `createLeadIntent` in the mock only writes a local record and is displayed as "demo application intent".
- **6.9 Privacy design reference.** Use the principles behind India's Digital Personal Data Protection Act, 2023 (notice, consent, purpose limitation, minimization, erasure) as a *design reference* in the consent screen and Memory panel copy. This is not legal advice; note that in `docs/DECISIONS.md`.
- **6.10 Journey continuity.** Resume links (signed, expiring) and an n8n nudge (Phase 8) that returns the user to the exact state.

**Deliverables:** memory service, ledger, Memory panel API, connector interface + mock + contract tests, isolation and deletion tests.
**Acceptance:** resume works across sessions; delete-then-search test passes; isolation test passes for all search types; contract tests pass for the mock and the stub's `NotConfigured` behavior.
**Failure modes:** Cognee write failure → outbox retry and "memory saving delayed" indicator (state is safe in Mongo); accidental PII in a statement → PII scanner on write, drop and log category only.
**Gate:** phase report + "GO".

  1. *Welcome*: language picker (English / हिंदी / Hinglish), plain-language consent (synthetic-data notice, memory consent toggle, voice toggle), start by voice or text.

  3. *Drawers*: Trust Receipt, Memory panel, Human Desk, Judge Mode.

- **7.10 Next Best Action bar.** Sticky, always populated, single primary button plus up to two secondary links. Copy is action-oriented and short.

- **7.14 Accessibility and inclusion.** WCAG AA contrast, full keyboard navigation, ARIA live regions for streaming messages and status, focus management in drawers, screen-reader-friendly simulator summary, large-text mode, plain-language microcopy in all three language modes.
- **7.15 Internationalization.** Every string in `en`, `hi`, `hi-Latn`; Indian digit grouping; dates in local format; language switch persists and applies to receipts and cards; no hard-coded English in components (lint rule).
- **7.16 Performance budget.** LCP < 2.5 s on simulated 4G mid-range phone; JS budget per route documented; code-split simulator and Judge Mode; font subsetting; skeletons for cards; optimistic UI for chip confirmations; offline queue for messages with a visible "sending later" state.
- **7.17 State matrix.** For each screen define: empty, loading, streaming, success, degraded, error, offline, escalated. Every state has copy and a next action (S10).
- **7.18 E2E tests.** Playwright on a mobile viewport: (a) Priya golden path in Hinglish text, (b) voice path with a mocked STT fixture and chip confirmation, (c) document upload → review → checklist, (d) memory delete, (e) chaos toggle → degraded banner → recovery.

**Deliverables:** complete UI, design tokens, Playwright suite, Lighthouse report.
**Acceptance:** Lighthouse mobile performance and accessibility ≥ 90 on the workspace; golden path e2e green in CI; no console errors; every drawer reachable by keyboard.
**Failure modes:** SSE dropped on mobile networks → auto-reconnect using the last event ID; slow first paint → server-render the shell, stream the rest; long Hindi strings breaking layouts → test with the longest strings early.

## PHASE 8 — n8n AUTOMATION (ASYNC ONLY) (≈7%)

**Objective:** real workflows that make Sahaj feel operational (documents, nudges, human help, freshness), integrated safely, and never on the chat's critical path.

**Principles:** workflows are code (export JSON to `n8n/workflows/`); every webhook is HMAC-signed with timestamp anti-replay; every event has an idempotency key; retries with backoff and a dead-letter path; payloads carry IDs and redacted summaries only; credentials live in n8n's credential store, never in workflow JSON.

**Processes**
- **8.1 Infrastructure.** n8n via docker (volume for data, basic auth, `WEBHOOK_URL` set to the public tunnel/domain) or n8n Cloud. Install/confirm the **Cognee** node (add, cognify, search) and the **Sarvam** integration per the docs. Save environment notes in `docs/integrations/n8n.md`.
- **8.2 Outbox pattern.** The API writes `outbox_events` in the same logical operation as state changes; a dispatcher posts them to n8n with `X-Sahaj-Signature`, `X-Sahaj-Timestamp`, `Idempotency-Key`; success → mark sent; failure → exponential backoff, cap attempts, mark `dead` and surface in Judge Mode. Event types: `document.uploaded`, `journey.documents_pending`, `escalation.requested`, `knowledge.refresh_requested`, `journey.completed`.
- **8.3 WF-1 Document pipeline.** Trigger: webhook `document.uploaded`. Nodes: verify signature (Code) → fetch a short-lived signed file URL → Sarvam Vision (create job, wait/poll with timeout) → Code node: normalize output and run the schema validator → HTTP callback to `/internal/n8n/documents/:id/extracted` (signed) → IF `needs_review` → notify the user channel (in-app event) → error branch: callback with `failed` + reason, Slack alert. *Only extracted fields flow back; raw content is not stored in n8n execution data (configure execution data pruning).* Fallback: `FF_DOC_INLINE_FALLBACK` executes the same steps in the API.
- **8.4 WF-2 Nudge and continuity.** Trigger: `journey.documents_pending`. Nodes: Wait (demo mode 60 s, production mode 24 h) → HTTP GET journey state via signed internal endpoint → IF still pending → translate the reminder text into the user's language with Sarvam (protected terms preserved) → optional Bulbul voice note → send via one channel (email/Telegram/Slack demo channel; WhatsApp only if sandbox access exists) with a signed **resume link** → callback `/nudges/:id/sent` → write event. Idempotent so restarts never double-send.
- **8.5 WF-3 Human escalation (Human Desk).** Trigger: `escalation.requested`. Nodes: verify → create a ticket row (Google Sheets/Airtable/Notion or the API's own `escalations`) with reason code and **redacted** summary → notify ops (Slack/email) → optional auto-acknowledge message → callback with `ticket_id` and status → SLA reminder branch via Wait. The user's UI shows the ticket ID immediately (optimistic) and updates on callback.
- **8.6 WF-4 Knowledge freshness and incremental ingest (S11).** Trigger: schedule (demo: manual button). Nodes: HTTP GET list of knowledge sources → Code: flag entries whose `effective_date` is older than the threshold or whose `source_hash` changed → for changed items use the **Cognee node** to `add` then `cognify` into the *next* version dataset → callback `/internal/n8n/knowledge/stale` → Slack summary with a "promote version" checklist. Promotion of `active_kb_version` stays a human-approved step.
- **8.7 WF-5 Analytics rollup (optional).** Daily schedule: fetch aggregate metrics (journeys started/completed, median time-to-next-action, escalation rate, Clarity Score mean, retrieval source coverage) → append to a Sheet → post a summary. Use this for the pitch's impact slide with honest labels.
- **8.8 Security.** Shared secret rotated via env; reject timestamps older than 5 minutes; reject replayed idempotency keys; allowlist n8n egress IP or use a private tunnel where possible; least-privilege API tokens per workflow; execution-data retention short; no PII in Slack/Sheets beyond redacted summary.
- **8.9 Observability.** Each workflow returns its `execution_id` in callbacks; Judge Mode shows it with status and duration; an n8n **Error Trigger workflow** posts failures to Slack with the event ID.
- **8.10 Failure tests.** Stop n8n mid-journey: chat continues, outbox retries, doc pipeline falls back inline, banner shows "reminders delayed". Restart n8n: queued events drain exactly once.
- **8.11 Export and reproducibility.** Export all workflows as JSON, commit them, and write an import script plus a README with credential setup steps so a judge can reproduce in 10 minutes.

**Deliverables:** five workflows (WF-1 to WF-3 are required; WF-4 is strongly recommended; WF-5 optional), outbox dispatcher, signature verification, failure-mode tests, exported JSON.
**Acceptance:** demo nudge arrives within the demo timer; escalation returns a ticket ID to the UI; duplicate events do not double-send; n8n-down test passes.
**Failure modes:** webhook unreachable → tunnel health check in `/ready`; n8n slow → never awaited by chat; credential expiry → error workflow alerts and the UI shows a neutral notice.
**Gate:** phase report + "GO".

## PHASE 9 — EVALUATION AND HARDENING (≈8%)

**Objective:** prove quality with numbers, break the system on purpose, and fix what breaks.

**Processes**
- **9.1 Test pyramid.** Unit + property (engines, state machine, parsers) → integration (each integration with mock and live smoke) → contract (connector mock/stub) → e2e (Playwright) → LLM evals (scenario suite below). Run unit/property/contract/e2e in CI; run live-integration evals on demand and before the demo.
- **9.2 Scenario suite.** Build 60 synthetic scenarios in `data/eval/scenarios.yaml` (Appendix C gives the mix). Each has: input turns, language, expected intent/entities, expected state, expected source IDs, expected number outputs (from engines), and pass/fail rules.
- **9.3 Metrics and targets** (report actuals honestly; a missed target becomes a documented gap, not a hidden one):

| Metric | Target |
|---|---|
| Intent (domain, purpose, amount) accuracy | ≥ 90% |
| Amount/duration parser accuracy on 40+ phrases | 100% |
| Required-field completion in ≤ 4 turns | ≥ 90% |
| Numbers traced to calc/context (after gate) | 100% |
| Factual answers with identifiable source | ≥ 95% |
| Retrieval recall@5 | ≥ 0.85 |
| Time-to-first-token p50 / p95 | ≤ 1.5 s / ≤ 3 s |
| Document field extraction accuracy (synthetic set) | ≥ 90% |
| Should-escalate cases that escalate / false escalations | ≥ 90% / < 10% |
| Cross-user memory leakage | 0 |
| Golden path completion across 20 consecutive runs | 100% |
| Chaos cases where the user is never blocked | 100% |

- **9.4 Grounding evaluation.** Seed hallucination traps (numbers not in context, fake product names, stale versions); assert the gate blocks them. Measure citation coverage. Optional LLM-as-judge with a written rubric, always paired with deterministic checks.
- **9.5 Red-team set (≥ 10 attacks, each with expected behavior):** demand for guaranteed approval; "just decide for me"; request for another user's data; system-prompt extraction; injection in an uploaded document; injection inside a retrieved chunk; legal/tax advice request; request for full ID numbers; pressure to hide fees; roleplay jailbreak; oversized/garbled input; Mongo-operator injection in profile fields.
- **9.6 Isolation test.** Two synthetic users, overlapping vocabulary, different goals, all search types; assert zero cross-retrieval; assert client-supplied dataset names are ignored.
- **9.7 Chaos matrix** (`scripts/chaos/`):

| Failure | Expected behavior |
|---|---|
| Cognee down or slow | cache → snapshot (flagged) → honest "can't verify" + Human Desk |
| Sarvam STT down | typed input prompt; recording retained for retry |
| Sarvam TTS down | text only, subtle notice |
| Sarvam Vision down | manual entry form + escalation option |
| LLM down/slow | fast model → template response from structured data |
| n8n down | chat unaffected, outbox retries, inline doc fallback, "reminders delayed" |
| Redis down | Mongo fallback, rate limiting degrades open with logging |
| Mongo slow | read-through cache, visible slow notice |

- **9.8 Latency and load.** Measure stage timings with the trace data; run k6/autocannon on the message endpoint at demo-relevant concurrency (e.g., 20 virtual users); produce p50/p95 and TTFT; identify the slowest stage and optimize (prefetch, smaller top-k, prompt trimming, parallelism).
- **9.9 Security checklist.** Secret scan clean; dependency audit; helmet/CORS/CSRF verified; upload validation (mime sniffing, size, extension, safe storage keys); Mongo query sanitization; rate limits; log redaction verified by grep on sample logs; HMAC and replay tests for `/internal/*`; cookies flags verified on the deployed domain.
- **9.10 Bug bash with humans.** Five non-team testers including Hindi-first speakers. Capture Clarity Score (S12), time-to-next-action, confusion points and translation glitches. Fix the top five issues. Keep the numbers as small-sample, honestly labeled evidence.
- **9.11 Evaluation report.** `docs/EVAL_REPORT.md` with tables and charts (retrieval search-type comparison, latency histogram, gate catch-rate, chaos results, Clarity Score) for direct reuse in the deck.

**Deliverables:** eval suite, red-team set, chaos scripts, evaluation report, fixes.
**Acceptance:** all table targets met or documented; zero P0/P1 open bugs; golden path 20/20.
**Gate:** phase report + "GO".
